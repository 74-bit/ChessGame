# 中国象棋（网页版）

纯静态页面，无依赖、无构建、无服务端。**双击 `index.html` 即可开始**。

## 三种模式

- **人机对战** — 三档棋力（简单 / 普通 / 困难），可选执红先手或执黑后手。
- **双人对战** — 同一设备上两人轮流走棋。
- **联机对战** — 纯前端 WebRTC 点对点，双方交换一次配对码即可开局，不经过任何服务器。

## 功能一览

**对局**：点击选中再点目标落子（绿点可走、红圈可吃、黄框上一步）；被将军时状态栏变红、将/帅闪烁；
悔棋、认输、重新开始、翻转棋盘（执黑时看着舒服）；
右侧按中文记谱法记录着法（如 `炮二平五`、`馬2进3`）。

**分析与评分**：实时胜率条 + 数值优势（`+1.4` = 领先一个半兵）、整盘胜率走势曲线、
每步的失误标记（`?!` 疑问手 / `?` 失误 / `??` 漏着）、终局百分制评分。

**其他**：走子音效（WebAudio 现场合成，不含任何音频文件）、复制棋谱到剪贴板、
棋力/执子/音效/翻转等设置记在 localStorage 里，下次打开还是上次的样子。

### 对话面板

**只有联机对战才有**，和对手实时聊天。带一组快捷短语（你好，开始吧 / 好棋！/ 快点吧 / 再来一局？），
回车发送，单条上限 200 字符，本地还有 400ms 的连点保护。人机和双人模式不显示对话面板。

### 快捷键

| 键 | 作用 |
|---|---|
| `U` | 悔棋 |
| `F` | 翻转棋盘 |
| `N` | 重新开始 |

## 规则实现说明

- 完整实现蹩马腿、塞象眼、象不过河、兵过河后可横走、炮隔子吃、九宫限制。
- **白脸将**（双方将帅同列且中间无子）按非法局面处理：将被视为可以直接"吃"掉对方将帅，
  这样既堵住了送将的着法，也让"飞将"能自然参与将军判定。
- **困毙判负**：与部分棋类不同，象棋中无棋可走同样判负，代码里区分显示"将死"与"困毙"。

### 将军不限制走子

本作**刻意放开了应将限制**：被将军时你仍然可以走任何"走得动"的棋子，
包括那些完全不解将的着法。系统只提示"红方被将军！可不应，但对方会吃将"，
不阻止你落子。

代价是胜负逻辑随之改变：

- **将/帅被吃即终局**，显示为"擒王获胜"。这是放开限制后最主要的胜负方式。
- 将军从一个"必须回应的威胁"降级为一个"警告"。
- 电脑仍然按标准规则走棋——它不会自己送将，但**你送它一定会吃**。
- 将死/困毙的判定保留：真的无棋可走时仍然判负，只是现在这种情况很少出现。

代码上为此把两个着法列表分开：`playableMoves`（伪合法，玩家点得动的）与
`legalMoves`（完全合法，只用来判定将死/困毙）。联机模式收到的着法也只校验
"这个子能不能这么走"，不再要求必须应将。

## AI 设计

negamax + Alpha-Beta + 迭代加深 + 静态搜索，外加 PVS、LMR、null-move 剪枝和 Zobrist 置换表。
着法排序用 置换表着法 → MVV-LVA → killer → history。

评估函数除子力 + 位置表外，另有两项能真正拉开差距的因素：

- **缺士怕车** —— 对方车马炮越多，己方缺士象的代价越大
- **车占开放线** —— 所在纵线双方都没兵时，车的价值明显更高

这两项在做同一次 90 格扫描时顺带算出来，几乎不增加开销；加上之后"困难"档的实测深度从 6 层升到了 8 层。

**开局库**（`OPENING_BOOK`）覆盖中炮对屏风马、反宫马、列炮、顺炮、仙人指路、飞相局等常见套路。
好处是开局不至于走出莫名其妙的自损着法，而且同一局面有多个分支时会随机挑一个，不会每盘棋都一模一样。
库里的着法仍会用本地规则校验一遍，不合法就当没有。

两个贯穿全局的约定：

1. **搜索内部走伪合法着法**，靠"吃到将/帅即判胜"兜底，只在根结点过滤完全合法着法。
   省掉每个结点 O(40) 次自将判定；根结点仍然只会走出合规棋。
2. **迭代加深带"下一层搜不搜得完"预判**：若上一层耗时 ×4 已超过剩余预算就收手，
   不把时间烧在注定被丢弃的迭代上。因此残局子力少时会自动算得更深。

棋力档位（`js/game.js` 的 `DIFFICULTY`，实测于初始局面）：

| 档位 | 迭代上限 | 时间预算 | 实测深度 | 实测耗时 |
|---|---|---|---|---|
| 简单 | 2 | 600ms | 2 | ~6ms，且在同分着法里随机挑，每盘不重样 |
| 普通 | 5 | 900ms | 5 | ~60ms |
| 困难 | 24 | 9000ms | 10–11 | 3–8s |

困难档每步要想好几秒——这是有意的，它比另外两档强出一大截。

加入置换表和剪枝前后的对比（同样搜到第 6 层，初始局面）：

```
优化前  1450107 结点  920ms
优化后   300450 结点  233ms     结点数降到 1/5，耗时降到 1/4
```

### AI 不占用主线程

搜索跑在 **Web Worker** 里，所以电脑思考时界面完全不卡：棋子动画照常播放、按钮照常可点。
状态栏下方会实时显示电脑搜到的深度和结点数。

这里有个 `file://` 带来的约束：既不能用 `importScripts()` 加载本地脚本，
也不能 `fetch()` 读源码（真实用户的 Chrome 会以 CORS 拦掉）。
所以 `rules.js` 和 `ai.js` 都写成**具名工厂函数**，主线程把它们的源码
`toString()` 出来拼成一个 Blob 当 Worker 跑，main 线程和 Worker 共用同一份引擎代码。
Worker 万一创建失败或中途挂掉，会自动退回主线程继续算，不会让对局卡死。

棋子定位也从 `left/top` 改成了 `transform: translate()`——后者能交给合成层渲染，
主线程即使被占住，滑行动画也不会僵在半路。

## 实时胜率与终局评分

胜率换算用 logistic：`胜率 = 1 / (1 + 10^(-评分差/250))`。
系数 250 是特意调陡的——最早用 400 时一个兵的优势才 64%，整盘棋胜率条几乎不动，
看不出局势起伏；现在 250 分（两个半兵）就到约 90%。

对局结束后给出**评分（满分 100）**：

```
总分 = 结果分 + 质量分

结果分（0~50）   胜 50，负 0

质量分（0~50）   由平均每步损失(ACPL)换算：50 × exp(-ACPL / 110)

  每步损失 = 走子前局面对该方而言的价值 − 走子后的价值，只取非负部分。
  下出最优着法时约为 0，失误越大越高。
```

等级：≥85 为 S·神级，≥70 为 A·优秀，≥55 为 B·良好，≥40 为 C·一般，其余 D·待提高。
面板同时列出结果分、质量分、平均每步损失、最大失误（含回合数）和吃子数。
**人机对战只给玩家打分**，双人和联机模式两边都给。

同一套"每步损失"数据还驱动着胜率曲线图和着法列表里的失误标记。

评估跑在 Worker 里，用固定 6 层深度（约 250ms），不占用主线程。
忙不过来时会主动丢弃中间采样点，宁可评分少几个样本，也不让胜率条一直卡在旧值上。

实测校准：认真下（5 层）对简单电脑 48 手取胜得 **100 分（S）**；
故意乱下对困难电脑 13 手被将死得 **9 分（D）**，平均每步损失 187、最大失误 2408。

## 联机对战

```
房主 创建房间  ->  房号 7K2MA  ->  告诉朋友
朋友 输入房号  ->  自动连接，房主执红先手
```

只要 **5 个字符**。要做到这一点必须有个中间人：WebRTC 的 DTLS 指纹由浏览器随机生成、
无法自定义或省略，光它就有 32 字节（base64 后 43 个字符），一条完整的连接信息最少约 100 字节，
5 个字符最多承载 30 bit，差了 25 倍以上。所以房号只是"房间名"，
真正的 offer/answer 通过**免费的公共 MQTT broker** 转发（默认 broker.emqx.io，
失败会自动依次尝试 hivemq、mosquitto）。

```
房主   订阅 room/a -> 生成 offer  -> retained 发布到 room/o
加入方 订阅 room/o -> 收到 retained 的 offer -> 应答 -> retained 发布到 room/a
房主   收到 answer -> setRemoteDescription -> 数据通道建立（此后点对点直连）
```

双方都先订阅再发布，配合 MQTT 的 retained 消息，加入方哪怕晚一步也能拿到 offer。
连上之后会把 retained 清掉，不给 broker 留垃圾。

MQTT 客户端是自己写的（只用到 CONNECT / SUBSCRIBE / PUBLISH-QoS0 / PING，
为此引一个上百 KB 的 CDN 库不划算），所以**没有任何前端依赖**。

**想自建 broker**：加个查询参数即可，多个用逗号分隔。

```
index.html?broker=ws://192.168.1.5:9001
```

仓库里带了一个能跑的最小 broker 和静态服务，方便自测：

```bash
bun test/mqtt-broker.js 9001      # 最小 MQTT broker
bun test/serve.js 0.0.0.0 8080    # 静态托管，局域网内可直接访问
```

注意 `file://` 被浏览器视为安全上下文，**会拦掉 `ws://` 的中转连接**（混合内容）。
所以本地用 `ws://` 自测时要用 `test/serve.js` 以 `http://` 打开；连公网 `wss://` 则不受影响。

防护措施：

- 每条走子消息带步数序号，对不上就提示局面可能已不一致。
- 收到的着法只校验"这个子能不能这么走"，非法着法直接忽略。
- 收到的聊天文本走 `textContent` 写入，不经过 HTML 解析，天然免疫注入。
- 轮不到自己时不能操作，悔棋在联机模式下禁用。
- 断线、对方认输、再战（自动交换先后手）都有对应处理。

已知限制：

- **需要联网**，且依赖公共 broker 的可用性。
- 连接信息会经过第三方服务器。房号只有 5 位（32^5 ≈ 3300 万种），
  理论上有人盯着 broker 是可以撞上的。**别用它传敏感信息。**
- 只用了公共 STUN，没有 TURN。双方都在严格 NAT / 对称 NAT 后面时可能连不上。
- 房号没有占用检测：两个人恰好随机到同一个房号会串到一起（概率极低）。

## 测试

三套测试都是纯函数级别的，能在 bun 里直接跑，不需要浏览器。

`perft.js` 对照中国象棋初始局面的标准节点数，四层全部吻合：

```
perft(1) = 44
perft(2) = 1920
perft(3) = 79666
perft(4) = 3290240
```

任何一条走法规则写错（马腿、象眼、炮架、河界、九宫）都会立刻让这组数字对不上，
所以这是比零散单测更硬的回归保险。此外还覆盖白脸将、蹩马腿、塞象眼、
兵过河、应将、不送吃等用例；`ai.js` 覆盖杀棋识别、应将正确性、搜索速度与自我对弈合法性；
`online.js` 覆盖两块纯逻辑：房号生成与规范化（含全角折半角、长度、字符集、随机性），
以及自写 MQTT 客户端的编解码——剩余长度变长整数的边界值、各类报文的类型与标志位、
粘包/拆包/逐字节喂入、UTF-8 往返、空载荷（清除 retained 用）。

这套测试抓到过一个隐蔽问题：`a=ice-ufrag:` / `a=ice-pwd:` 前缀长度数错一位
（写成了 11 和 9，正确是 12 和 10），解析出的凭证都多一个前导冒号。
**这个 bug 不影响连接成功**——两端用的是同一套错误值，Chrome 容忍了，
所以只靠手工点两下根本发现不了。后来改成用常量取长度，杜绝这类数错。

## 已知限制

- 未实现重复局面判和（长将、长捉等专业规则），超长对局需要手动重开。
- 联机模式没有悔棋协商机制（悔棋被禁用）。
- 联机模式没有聊天和观战。
- 没有对局回放/逐步复盘，错过的局面只能靠悔棋倒回去看。
